1"""Agentic-loop turn evaluator. 

2 

3After each reply turn that produces natural-language content, a small LLM 

4decides whether the loop should terminate (the agent has done what it can 

5with its current allow-list) or keep working (a tool in the allow-list 

6could directly perform the user's expressed action but the agent replied 

7in prose instead). 

8 

9Contract is binary: terminal vs continue. "Satisfied" and 

10"needs_user_input" are both terminal from the loop's perspective — both 

11mean stop looping and hand back to the user. 

12 

13Fail-open on parse or transport failure collapses to ``terminal=True``. 

14Spinning a broken loop is worse than delivering a possibly-weak reply. 

15"""

83 "the specific tool the agent should call next and what to pass.\n\n"

104 "an extra turn just because the turn reads conversationally.\n" 

105 " - For MULTI-PART queries: count the parts. If every part is " 

106 "addressed with concrete facts in the reply, terminal. If at least " 

107 "one part is unaddressed or not yet answered, return continue and " 

108 "nudge for the missing part.\n\n" 

109 "GARBLED / MALFORMED TURNS: if the agent's turn is not readable " 

110 "English prose — for example it contains raw tool-protocol markers " 

111 "like `tool_code` or `tool_output` blocks, special sentinel tokens " 

112 "like `<unused88>` (or any `<unused…>` variant), bare `tool_calls:` " 

113 "text, truncated JSON, or code/data dumps where a natural reply " 

114 "should be — return \"continue\". Shipping garbled text to the " 

115 "user is worse than one extra turn. The engine also catches the " 

116 "known shapes deterministically; your job here is defence-in-depth " 

117 "for novel leaks.\n\n" 

118 " SALVAGE a failed tool call when you can. If the garbled turn " 

119 "looks like the agent tried to invoke a tool but emitted the " 

120 "protocol as text — e.g. `tool_code\\nprint(google_search.search(" 

121 "query=\"sam smith biography\"))`, or a bare `tool_calls: " 

122 "[{\"name\": \"webSearch\", \"arguments\": {\"query\": \"...\"}}]` " 

123 "JSON blob, or a `<unused…>` block wrapping a tool invocation — " 

124 "extract the intended tool and arguments and name the tool in the " 

125 "nudge, e.g. \"call webSearch with query='sam smith biography'\". " 

126 "Only name a tool that actually appears in the toolbox above; if " 

127 "the extracted tool is not in the allow-list, pick the closest " 

128 "matching tool or fall back to a \"produce a natural-language " 

129 "reply\" nudge. If the garbled turn is unrecoverable (truncated " 

130 "JSON with no name, bare `<unused88>` with no content, random " 

131 "data dump), nudge \"produce a natural-language reply\" instead. " 

132 "Do NOT fabricate arguments the garbled turn did not contain.\n\n" 

133 "When in doubt: for MULTI-PART queries with any part unaddressed, " 

134 "prefer continue — a wasted extra turn is cheaper than handing back " 

135 "a half-answer. For SINGLE-PART queries whose ask is already " 

136 "addressed by concrete facts in the turn, prefer terminal — looping " 

137 "past a good answer burns the agentic-turn budget, which fires the " 

138 "max-turns digest summariser and prepends a \"could not fully " 

139 "finish\" caveat onto an otherwise correct reply. That caveat is a " 

140 "worse UX than terminating on the grounded reply.\n\n" 

141 "STRUCTURED TOOL CALL: whenever you name a specific tool AND " 

142 "arguments in the nudge (salvage path, or an obvious missed " 

143 "invocation), ALSO emit a structured `tool_call` field with the " 

144 "exact same intent. The engine uses it to execute the call directly " 

145 "on behalf of the agent — this is the only reliable path when the " 

146 "chat model is a small one that tends to ignore textual nudges. " 

147 "Shape: `\"tool_call\": {\"name\": \"<toolName>\", \"arguments\": " 

148 "{<k>: <v>, ...}}`. The `name` MUST appear in the toolbox above. " 

149 "`arguments` must be a JSON object — use `{}` when the tool takes " 

150 "none. OMIT the field (or set it to null) when you are nudging for " 

151 "prose (\"produce a natural-language reply\") or when you cannot " 

152 "identify the exact arguments — never fabricate arguments you did " 

153 "not extract from the garbled turn or derive from the user query.\n\n" 

154 " ARGUMENT KEYS MUST BE EXACT. Each tool in the toolbox is listed " 

155 "with its parameter signature, e.g. `webSearch(search_query: string " 

156 "required)`. When you emit `arguments`, use those exact parameter " 

157 "names verbatim — do NOT invent plausible-sounding alternatives " 

158 "(\"query\" when the schema says \"search_query\", \"url\" when it " 

159 "says \"page_url\"). The engine will reject a call whose keys do " 

160 "not match the schema. If the toolbox entry shows no parameters, " 

161 "pass `{}`. If you are unsure what arguments a tool takes, omit " 

162 "`tool_call` entirely and nudge in prose.\n\n" 

163 "Only two outcomes. Output strict JSON only, no prose, no code fences:\n" 

164 " {\"terminal\": <bool>, \"nudge\": \"...\", \"reason\": \"...\", " 

165 "\"tool_call\": {\"name\": \"...\", \"arguments\": {...}} | null}\n\n" 

166 "The \"nudge\" field is empty when terminal is true. The \"reason\" " 

167 "field is a short log hint, never shown to the user. The " 

168 "\"tool_call\" field is null when terminal is true or when no " 

169 "specific tool invocation was identified.\n" 

170 "Do NOT answer the user's query yourself. Do NOT add commentary."
